# 质量、运营与实施路线图

App 版本：1.0

日期：2026-08-10

状态：需求讨论中

## 1. 交付策略

按照“数据与信任地基 → 真人发现 → App 1.0 平台话题与手动运营 → 未来在线商业化 → 本人认领 → 可选平台扩展”推进。每个阶段必须形成可验证、可回滚、可运营的闭环，不把授权、平台接收披露、审核、账本或数据权利留作上线后的补丁。

## 2. 工作流

| 工作流 | 范围 | 横向依赖 |
|--------|------|----------|
| P 产品与设计 | PRD、流程、文案、线框、高保真、可访问性 | 所有阶段 |
| D 数据与迁移 | Person/Profile、授权、映射、投影和迁移 | App 1.0–后续阶段 |
| B 共享后端 | 账号、发现、互动、消息、商业和审核 | App 1.0–后续阶段 |
| C KMP 客户端 | App 1.0 Android/iOS，共享业务和 UI；普通用户 Desktop 未立项 | M1–后续可选阶段 |
| A 管理后台 | 真人、代运营、商品、调币、认领和审计 | M0–M3 |
| S 信任与安全 | 认证、授权、举报、风控、隐私和事件响应 | 所有阶段 |
| O 运营与客服 | 内容供给、排班、SLA、商品和申诉 | App 1.0–后续阶段 |
| Q 质量与发布 | 测试、压测、可观测性、恢复和门禁 | 所有阶段 |

### 2.1 当前开发进度说明

Privacy-1 已完成默认关闭的跨仓开发基线：App API v2 累计为 `1.17.0`，Cloudflare 已具备数据权利策略、申请状态机、二次验证、申请级状态访问、Nuxt 管理队列与 Operations-1 逾期检测，KMP 已具备响应式申请、记录、详情和取消交互。当前只支持安全登记、追踪和取消；真实导出制品、下载与不可逆注销处理属于 Privacy-2。按当前开发顺序，环境配置、`0094` 执行和专项测试统一后置。

## 3. M0：数据与产品地基

### 3.1 目标

在不改变现有 Web 行为的前提下，冻结正确领域模型和共享契约，建立真实可导入的供给与商业底座。

### 3.2 交付

- 产品总纲、Feature PRD、移动端/后台页面交互规格、统一状态文案与埋点目录和决策清单。
- `Account`、`Person`、`PersonProfile`、`Gallery`、授权、认证、运营和认领模型。
- MeiGallery 数据盘点、stable ID、影子映射、导入和对账方案。
- 心享会员五级、entitlement、商品、订单、钱包和只追加账本模型。
- KMP/CMP 库组合与平台边界基线：Jetpack KMP、Ktor、Coil、Room/DataStore，以及 Media3/AVPlayer 视频适配方案。
- 后台 RBAC、审计、内容/财务职责分离。

### 3.3 退出条件

- 所有公开人物候选默认不可见，缺少授权证据不能发布。
- 普通账号不会生成真人资料。
- 数据模型、API schema、权限和迁移有评审结论。
- KMP Android/iOS 空壳完成统一版本锁；网络、序列化、Paging、Room、DataStore、Coil 受保护缓存、WebSocket 和 Media3/AVPlayer HLS 技术验证通过（进入实现阶段后执行）。
- Android 设备矩阵从 API 26 开始，API 25 及以下不设置兼容用例或发布门禁。
- M1 必需开放问题关闭，风险和负责人明确。

## 4. M1：真人发现闭环

### 4.1 目标

让受控用户能够安全注册、发现已认证真人、查看媒体并进行单向互动，同时让管理员完成供给和审核闭环。

### 4.2 用户能力

- 注册、登录、设备和隐私设置。
- 推荐、地区、热门、最新、搜索和筛选。
- 真人详情、图库媒体、喜欢、关注、收藏和浏览历史。
- 通知、举报、拉黑、帮助，以及数据导出/注销的申请、进度和允许阶段取消；真实导出下载与不可逆处理必须通过 Privacy-2 门禁。

### 4.3 后台与运营

- 真人上传、MeiGallery 导入、授权证据、认证、发布、暂停和归档。
- 标签、地区、推荐位、热度规则和公开投影。
- 举报队列、申诉、审计、值班和撤回演练。
- 数据权利总览、最小化申请队列、Owner 领取/处置、逾期检测和隐私事件 Runbook；不得在缺少真实处理证据时手工标记完成。

### 4.4 退出条件

- Android/iOS 核心旅程 E2E 通过。
- 所有公开入口只返回 `verified + published`。
- 暂停资料和媒体凭证撤回满足目标时限。
- 个性化关闭、非个性化入口和数据清除有效。
- 无障碍、性能、崩溃、数据权利和安全门禁通过；Privacy-2 未获批准时 production 数据权利 capability 保持关闭。

## 5. M2A：App 1.0 平台话题与手动运营

### 5.1 目标

上线五级心享会员目录与站内申请、披露式平台话题、管理员审核发放、站内通知，以及可对账的管理员金币调整闭环。

### 5.2 用户能力

- 五级会员比较、站内申请、状态查询、管理员发放、到期和权益刷新。
- 有效会员围绕真人资料发起由平台接收的话题，支持文本消息和会话控制。
- 金币余额和明细；金币不具现金价值，不提供购买、充值、消费、兑换、转账或提现。
- 会员、金币、消息和安全站内通知，不依赖系统推送。

### 5.3 后台与运营

- 平台话题队列、分配、平台身份回复、内部备注、响应和安全升级。
- 会员申请队列、entitlement、手动发放、有效期和撤销。
- 钱包、调币、双人复核、冲正和账本对账。
- 文本消息审核、举报、客服和安全争议流程。

### 5.4 退出条件

- 平台接收披露通过法务、用户理解和 UI 一致性检查。
- 管理员无法发送 `person` 身份消息或伪造本人状态。
- 消息顺序、幂等、重连、补拉、拉黑和撤权压测通过。
- 会员 grant、entitlement、调币和账本日对账无未解释差异。
- 调币阈值、双人复核、用户说明和审计通过演练。
- 限量 Beta 至少具备 80 个可公开真人资料、3 个地区组，且授权与认证有效率为 100%。
- 服务时段内至少 1 名平台运营在岗、1 名可接替人员，会员申请和平台话题队列容量支持邀请规模。
- 队列达到 70% 时预警、85% 时限流、100% 时暂停新话题；降级由服务端 capability 控制并给出真实用户说明。

M2A 的功能验收分别以 [会员与手动发放](../ways-of-work/plan/real-person-discovery-platform/membership-entitlements-and-manual-grants/prd.md)、[平台话题与运营接收](../ways-of-work/plan/real-person-discovery-platform/member-messaging-and-managed-operations/prd.md)、[站内通知](../ways-of-work/plan/real-person-discovery-platform/in-app-notification-center/prd.md)、[钱包与调币](../ways-of-work/plan/real-person-discovery-platform/wallet-ledger-and-admin-coin-adjustments/prd.md) 和 [运营看板与审计](../ways-of-work/plan/real-person-discovery-platform/operations-dashboard-and-audit-log/prd.md) 为准。

## 6. M2B：未来在线商业化

### 6.1 范围

- 商店购买、恢复、续订、升级、退款和订单对账。
- 金币充值、固定礼物、头像框、主页皮肤和聊天皮肤。
- 经审核的图片消息与系统推送。

### 6.2 进入条件

- 独立 Feature PRD、目标商店、支付/推送适配器、价格、退款和客户端版本门槛已冻结。
- 商店凭证、订单、entitlement、账本和库存日对账通过。
- 不能仅通过远程配置启用客户端未实现的支付、推送或虚拟商品能力。

## 7. M3：真人本人入驻

### 7.1 目标

让合格真人安全认领资料并接收新会话，同时保护代运营时期的消息和运营数据。

### 7.2 交付

- 认领申请、身份核验、授权复核、冲突和申诉。
- 账号绑定、资料字段权限、本人收件箱和运营模式切换。
- 新会话路由、历史交接同意、系统披露和撤回机制。
- 真人端安全、设备、通知和数据权利。

### 7.3 退出条件

- 冒领、重复认领、证据过期和争议演练通过。
- 新会话路由正确，历史会话默认隔离。
- 交接 consent、审批、审计和回滚验证通过。
- 真人本人消息与平台运营消息在 UI、API 和审计中清晰区分。

## 8. 可选平台与区域扩展

### 8.1 目标

按真实业务扩展多语言、多地区、视频和实验能力。普通用户 Windows/macOS 客户端不是承诺项，只有独立立项后才进入交付。

### 8.2 交付

- 若桌面客户端立项：Desktop 三栏布局、键盘、窗口、通知、安全存储、签名和更新。
- 多语言、地区目录、条款、支付/推送/身份适配和数据路由。
- 视频资料和经安全评审的新消息媒体。
- Web 按模块迁移到共享账号、权益、真人和内容核心。

### 8.3 退出条件

- 若桌面客户端立项：目标平台构建、签名、更新和回滚验证通过。
- 核心功能与移动端契约一致，平台差异有专项测试。
- 新地区法律、数据、商店、客服和内容供给门禁关闭。

## 10. 必测场景

### 10.1 真人与发现

- 普通账号永远不会进入真人列表。
- 未认证、未发布、暂停和归档资料在所有入口一致过滤。
- 授权撤回后媒体和分享链接停止可用。
- 推荐个性化关闭、规则切换和游标过期。

### 10.2 平台话题

- 无会员、会员到期、额度耗尽和客户端重试。
- 平台运营/本人运营身份、会话切换和系统消息。
- 多设备、断线、乱序、重复、DO 休眠和 HTTP 兜底。
- 拉黑、举报、账号冻结和资料暂停时的在途消息。
- 内部备注永远不进入用户 API。

### 10.3 App 1.0 会员与账本

- 会员申请提交、重复拦截、待补充、拒绝、取消、手动发放、到期、撤销和 entitlement 刷新。
- 低风险调币、高风险复核、批量部分失败和冲正。
- 余额重建、grant/entitlement/分录逐笔对账。

未来商业化启用时增加商店回调、恢复购买、退款、金币消费、赠礼、商品下架、库存和装扮到期场景。

### 10.4 认领

- 冒领、同一真人重复申请、同一账号认领多个冲突资料。
- 认领批准、撤回、争议和运营模式回滚。
- 无 consent 的历史消息访问必须失败。

## 11. 质量目标

性能和稳定性具体数值在容量与用户地区确认后冻结，但每项必须在实现前建立测量方式：

- App 冷启动、推荐首屏、详情和消息补拉延迟。
- API 成功率、D1/DO/Queue/Workflow 错误和积压。
- 消息发送成功、重复率、顺序错误和首次响应。
- 会员发放差异、账本差异和调币异常；订单指标在未来商业化启用后加入。
- 崩溃率、ANR、客户端版本分布和强制升级比例。
- 无障碍关键路径完成率和严重问题数。

核心正确性目标（越权、冒充、重复扣费、账本不平、无授权发布）不因性能预算而放宽。

限量 Beta 的产品与运营建议目标：

- 邀请用户完成首个真人详情访问不低于 60%。
- 详情访问用户产生关注或收藏不低于 30%。
- 有效会员完成首个平台话题创建不低于 20%。
- 合规新话题和会员申请的接收主体、当前状态与用户可见时间线可追踪率为 100%；具体处理时效指标在 OQ-010 关闭后另行冻结。
- 披露理解测试中正确回答“消息由谁接收”的比例不低于 90%。
- 未授权发布、管理员冒充本人、越权读取和账本不可解释差异为 0。

## 12. 可观测性

- Request/Trace ID 贯穿客户端、Worker、DO、Queue、Workflow 和适配器。
- Dashboard 分产品、消息、商业、安全、迁移和基础设施。
- 日志和分析禁止包含平台话题正文、证件、授权原件、完整支付凭证和访问令牌。
- 告警有严重级别、Owner、响应时限、Runbook 和升级渠道。
- 关键审计缺失、平台运营身份异常和账本差异属于高优先级事件。

## 13. 运营准备

### 内容运营

- 首批真人名单、授权完整率、资料质量、更新频率和争议渠道。
- 认证/发布、暂停和权利撤回排班与容量。

### 平台话题运营

- 服务时段、会话分配、响应目标、话术边界、禁止冒充培训和抽检。
- 高危内容升级、用户投诉和真人认领衔接。

### 会员、金币与客服

- App 1.0 五级权益说明、站内申请与状态、人工处理时段、有效期和调币授权。
- 未来商业化立项后再准备价格、续订、退款、订单、礼物和装扮争议流程。

### 安全与隐私

- 举报、申诉、高危事件、数据请求、账号注销和安全事件值班。

## 14. 发布门禁

每个候选版本至少完成：

- 需求与设计验收、开放决策检查和文案审核。
- API/数据 migration 兼容性、备份、回滚和数据质量验证。
- 自动化测试、目标设备 E2E、安全、隐私和无障碍测试。
- 商店、地区、数据、内容、客服、支付和财务检查（按版本范围）。
- 监控、告警、Runbook、值班、feature flag 和回滚演练。
- 发布说明和客服知识库与实际功能一致。

App 1.0 采用限量邀请 Beta。除通用候选版本门禁外，还必须满足 [产品决策基线](./APP_1_0_PRODUCT_DECISION_BASELINE.md) 中的供给完整度、运营排班、队列降级和安全事件目标；这些建议数值须在邀请前由客户与运营共同确认。

## 15. 需求文档完成定义

进入实现排期前，每个 Feature PRD 必须包含：用户、场景、入口、主流程、异常、状态、权限、安全、埋点、验收和不做项。价格、额度、供应商和地区等参数必须在对应最晚关闭点前进入决策登记；不得用“以后再说”替代规则。

需求讨论期间所有文档保持 App 版本 1.0，直接更新当前结论。App 发布新版本时再统一更新文档版本。

## 16. 项目级验收

- **OPS-AC-001**：App 1.0 与后续每个阶段均有范围、退出条件、Owner 和证据。
- **OPS-AC-002**：实现任务能追溯到 PRD 要求、设计状态、API/数据契约和测试。
- **OPS-AC-003**：没有授权、代运营、安全、财务或数据权利 Owner 的阶段不能公开发布。
- **OPS-AC-004**：发布失败可通过 feature flag、路由切换或 forward-fix 安全停止扩散。
- **OPS-AC-005**：核心正确性事件有告警、Runbook、值班和复盘。
- **OPS-AC-006**：文档、商店文案、客服话术和真实实现不存在接收主体或权益差异。
- **OPS-AC-007**：Given 平台话题队列达到配置阈值，When 系统降级，Then 新话题按 70%/85%/100% 策略预警、限流或暂停，历史内容与会话按安全规则保持可查看。
- **OPS-AC-008**：Given 用户提交会员申请，When 运营处理并由管理员发放，Then 申请状态、grant、entitlement、通知和审计可以端到端追溯。
