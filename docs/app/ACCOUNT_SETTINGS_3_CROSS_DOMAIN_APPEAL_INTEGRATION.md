# Account/Settings-3 跨领域申诉开发基线

App 版本：1.0

更新时间：2026-08-14

状态：开发已实现；migration、环境配置、构建、专项测试、Android/iOS 运行验证与远端联调按当前开发顺序后置

## 1. 目标与范围

Account/Settings-3 将 `APP-SET-08` 从“仅举报结论复核”扩展为统一的用户申诉入口，覆盖三类服务端权威来源：

- 举报结论：沿用 `app_safety_appeals`，仅对本人收到“未发现违规”的举报结论发起独立复核。
- 账号限制：针对当前账号限制版本创建业务申诉，来源快照包含用户安全的原因类别、限制期限和安全业务引用。
- 金币分录：针对本人不可变金币分录及其 sequence 创建业务申诉；申诉不修改余额，不覆盖或删除原分录。

三类来源共享提交、独立复核、补充说明、升级和终态展示规则，但不合并权威业务表，也不允许申诉工作流直接改写原业务对象。

## 3. 用户侧 API

累计 App API v2 契约为 `1.23.0`。

| 方法 | 路径 | 规则 |
|---|---|---|
| `POST` | `/api/v2/service-appeals` | 对账号限制或金币分录幂等创建案件；要求来源类型、来源 ID、预期来源版本和说明 |
| `GET` | `/api/v2/me/service-appeals` | 只返回本人案件，按 `updatedAt DESC, appealId ASC` 排序并使用账号绑定不透明游标 |
| `GET` | `/api/v2/me/service-appeals/{appealId}` | 返回本人来源摘要、用户可见状态、说明、补充和时间线 |
| `POST` | `/api/v2/me/service-appeals/{appealId}/supplements` | 使用 `expectedVersion` 与 `Idempotency-Key` 追加必要说明 |
| `POST` | `/api/v2/me/appeals/{appealId}/supplements` | 对举报结论申诉追加必要说明，使用相同版本和幂等边界 |

bootstrap 的 `capabilities.safety` 增加：

- `accountRestrictionAppeals`：Auth 与安全申诉能力均开启时才为 `true`。
- `walletEntryAppeals`：除上述条件外还要求 Wallet 能力开启。

未知、缺失或矛盾 capability 必须关闭入口。生产环境不因 migration 或代码存在而自动开放。

## 4. 数据与状态机

`0100_app_cross_domain_appeals.sql` 只增加数据结构，不启用环境：

- 为 `app_account_security` 增加单调限制版本、安全业务引用和原决定管理员引用。
- 为举报申诉增加 `review_state`、复核期限和补充期限。
- 新建 `app_service_appeals`、用户可见事件、补充说明和幂等事实表。
- 新建统一的跨来源复核事件与命令事实，用于补充请求、补充提交和升级。
- 事件、补充和命令表禁止更新或删除；服务申诉身份和原始证据字段不可变；终态不可再次变更。

用户可见状态映射：

| 内部状态 | 用户状态 |
|---|---|
| `submitted` | `submitted` |
| `triaged` / `investigating` | `processing` |
| `upheld` | `upheld` |
| `changed` | `changed` |
| `closed` | `closed` |

`review_state` 独立于业务状态：`normal`、`evidence_insufficient`、`needs_escalation`。升级不代表结论，且升级后用户不能继续补充。

## 5. 幂等、并发与隐私

- 创建和补充要求独立 `Idempotency-Key`，相同键与相同请求返回原结果；相同键复用到不同请求必须返回冲突。
- KMP 只在当前进程、当前申诉流程内保存待重试请求；正文不写磁盘、日志、埋点或崩溃报告。
- 网络响应丢失后的显式重试复用原请求标识，不能生成第二个案件或第二条补充。
- 同一来源版本已由另一设备创建案件时，客户端读取现有案件并进入处理或终态，不停留在不可执行失败态。
- 补充说明使用乐观版本；冲突时重新读取案件，若已升级或终结则立即退出编辑态。
- 用户列表与详情只返回用户可见文案，不返回来源内部证据、管理员备注、审核规则或内部 ID。

## 6. KMP 页面选择规则

- 从账号限制入口进入：只匹配同一账号限制 ID 与版本。
- 从金币分录入口进入：只匹配同一分录 ID 与 sequence。
- 从举报详情进入：只匹配该举报当前绑定的申诉 ID；没有绑定时显示创建页。
- 从通用 `/me/appeals` 进入：在举报申诉与业务申诉中按 `updatedAt` 选择最近更新案件。
- 举报申诉与业务申诉列表统一按 `updatedAt DESC, appealId ASC` 分页；客户端对具体业务来源在首屏未命中时继续使用不透明游标查找，不能把已有旧案件误判成可新建。
- 终态优先于通用创建页真实呈现；三个终态分别绑定自己的 Figma Node ID，不能复用处理中状态。

## 7. 管理后台边界

`ADM-SAF-03/04` 使用同一队列与工作台承载举报和业务申诉：

- 队列不返回申诉正文；领取后才按最小必要目的读取详情。
- 领取人不得是原业务决定管理员；服务与最终 SQL 条件均重新校验职责分离。
- 请求补充、升级、维持、成立或关闭均要求 `expectedVersion`、幂等键和不可删除审计。
- 结论只更新申诉状态。对原账号限制、举报或金币账本的任何后续动作必须进入各自权威工作流，不允许业务双写。
