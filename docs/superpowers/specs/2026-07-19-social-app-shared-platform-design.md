# 独立交友 App 与共享平台顶层设计

日期：2026-07-19

状态：共享平台与渐进迁移路线已获用户确认；细化设计待逐项评审
范围：产品与架构设计，不包含实现

## 1. 背景

用户提供的视觉稿展示一个以真人认证、同城发现、即时聊天、VIP 和金币为核心的独立交友 App。现有仓库是 MeiGallery Cloudflare 图库平台，已有账号、会员、授权媒体、标签、后台与审计能力，但没有交友资料、匹配、消息、举报或钱包领域。

用户确认：App 是独立产品，但需要使用当前项目数据，且当前 Web 未来也需要迁移，因此方案必须前瞻并支持渐进迁移。

## 2. 备选方案

### 方案 A：共享核心平台 + 渐进迁移（已选择）

建立版本化共享 API 和目标数据模型，新 App 从第一天使用 v2；现有 Web 保持运行，再按账号、权益、媒体和后台模块逐步切换。

优点：数据最终统一，迁移可分阶段验证，新旧客户端互不绑死。缺点：前期需要兼容层、迁移任务和双读对账。

### 方案 B：直接扩展现有 API

在当前 D1 与 Hono Worker 追加资料、匹配、消息和支付。

优点：启动快。缺点：Gallery/Profile、旧会员/商店权益、普通审计/财务账本持续耦合，未来迁移更难。

### 方案 C：全新平台 + 长期同步

新建完整后端，通过事件或定时同步旧数据。

优点：隔离强。缺点：长期双写、一致性、账号冲突和运营对账成本高。

## 3. 已选方向

选择方案 A。顶层原则：

- App 独立，数据核心共享。
- 账号复用不等于交友资料自动公开。
- Gallery 与 Profile 是不同聚合。
- 认证、VIP 和管理员身份独立表达。
- 实时消息、财务账本和全局查询使用各自合适的一致性模型。
- 先完成安全和迁移闭环，再开放商业化。

## 4. 产品设计

目标用户是年满 18 周岁的中文交友用户。核心旅程为：手机号/旧账号登录 → 新条款和成年人核验 → 创建并审核资料 → 推荐/附近/活跃发现 → 喜欢或受限招呼 → 双方同意后匹配 → 实时聊天 → 举报/拉黑/解除匹配。

首版不做随机匿名聊天、未成年人交友、聊天图片、语音视频、直播或提现。概念稿中的“精确 1km/2km”“无限次聊天”“VIP 身份标识”调整为模糊距离、匹配后畅聊、VIP 与认证徽章分离。

## 5. 架构设计

- 移动端：React Native + TypeScript。
- API：现有 Hono Worker 内新增 `/api/v2` 模块边界，容量或权限证明需要时再拆。
- 实时：独立 Worker + SQLite-backed Durable Objects；一段会话一个对象。
- 核心 D1：账号、同意、角色、权益、订单、钱包和审计。
- 社交 D1：资料、偏好、互动、匹配、举报、审核和会话投影。
- 媒体：私有 R2；后续视频使用 Stream signed URL。
- 异步：本地事务 + outbox + Queues；长任务使用 Workflows。
- 外部必需集成：APNs/FCM、应用商店支付、短信和合规身份核验。

## 6. 数据迁移设计

首批评估迁移：用户、会员、授权媒体、标签和管理员。Web session 不迁移，旧分析/广告数据不进入交友画像。

迁移顺序：盘点与用途分类 → `account_id`/legacy link → 影子迁移与对账 → 用户主动激活 → 权益双读与切换 → 媒体/标签授权迁移 → 后台与 Web 模块迁移 → legacy 只读归档。

每类数据在任何阶段只能有一个写权威。迁移条目必须可重入、可追溯、可隔离失败，并保留回滚锚点。

## 7. 错误与恢复

- 客户端写操作使用幂等键。
- 消息按 Durable Object 序号补拉，投影失败不丢权威消息。
- 跨域事件至少一次投递，消费者按 `event_id` 幂等。
- 支付、退款和人工调整只追加账本分录或冲正。
- 数据迁移失败回到旧写权威；新 App 已生成的消息、订单和举报保全只读，不反写 legacy。

## 8. 测试设计

重点覆盖账号绑定冲突、授权撤回、媒体权利、匹配状态机、拉黑竞态、消息重连/重复/休眠、账本并发、商店回调乱序、注销与安全证据保留、D1/R2/DO 恢复和迁移回滚。

公开发布前要求：API/消息 SLO、举报 SLA、账本零不平衡、商店 sandbox、商店政策、APP 备案、数据跨境和删除演练全部通过。

## 9. 关键风险

最高风险不是技术实现，而是把图库人物误表示为真实交友用户、未成年人访问、诈骗骚扰、资金账本错误，以及在未确认 Cloudflare 数据路径的情况下处理中国大陆敏感个人信息。

因此数据授权、成年人认证、拉黑举报、账本和中国大陆数据/备案结论均为上线硬门禁。

## 11. 自检结论

- 无未定义字段或缺失章节。
- 现有 Web 的已实现能力与 App 目标态使用状态标签区分。
- 产品边界、数据权威、消息权威和商业账本不存在相互矛盾定义。
- 开放商业/法务问题集中进入 OQ 登记表，均有最晚关闭点和决策角色。
- 设计范围可拆分为独立工作流，不要求一次性重写现有系统。
