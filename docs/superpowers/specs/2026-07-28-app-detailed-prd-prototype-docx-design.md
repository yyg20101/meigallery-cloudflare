# MeiGallery App 1.0 详细功能与原型 DOCX 重构设计

日期：2026-07-28

状态：方案已确认，待实施

## 1. 背景与问题

现有《产品需求确认书》共 35 页，只包含 7 张按旅程拼接的原型截图；《逐页交互设计确认册》共 16 页，只包含 2 张页面库总览图。当前文档无法让客户按功能逐项确认，也存在标题、功能说明与截图内容错位的问题。

已确认的典型错位包括：

- “启动、注册与登录”章节使用推荐列表截图。
- “真人详情与媒体”章节使用会员门槛截图。
- “站内通知”章节主要展示金币钱包。
- “真人上传与 MeiGallery 导入”章节使用内容审核工作台截图。
- “平台话题代运营工作台”章节混入会员发放和金币调整表单。

本轮重构的目标不是简单增加图片，而是建立可自动校验的“功能—页面—状态—截图—验收”一一映射。

## 2. 已确认的重构范围

采用完整逐功能确认方案：

- 92 个 Page ID 全部提供独立、对应的默认状态原型图。
- 54 个 P0 页面各补充 1 个最关键的异常、受限或处理中状态图。
- 默认状态截图 92 张，P0 关键状态截图 54 张，合计 146 张。
- 每个功能页面都包含详细说明、精确截图、状态与验收，不再使用含多个页面的旅程截图代替单页原型。
- App 业务代码、KMP 工程、API 和数据库均不在本轮范围；允许调整文档原型的捕获模式和生成脚本。

## 3. 交付物

### 3.1 客户主文档

输出文件：

`docs/app/deliverables/MeiGallery_App_1.0_产品需求确认书.docx`

定位：客户需求确认、产品设计、研发估算和测试验收的完整业务基线。

结构：

1. 产品定位、角色、范围和不可变边界。
2. 端到端业务流程、会员、金币、运营和安全规则。
3. 移动端详细功能与对应原型。
4. 管理后台详细功能与对应原型。
5. 关键状态补图。
6. 非功能需求、数据迁移、指标和验收。
7. 客户确认事项、逐功能确认清单和签字页。

### 3.2 逐页交互确认册

输出文件：

`docs/app/deliverables/MeiGallery_App_1.0_逐页交互设计确认册.docx`

定位：按 Page ID 进行逐页评审、记录修改意见和验收结果。

每个 Page ID 使用独立确认单元，并与主文档使用同一截图资产和同一功能元数据，禁止维护第二套手工文案。

### 3.3 Markdown 与映射清单

新增或更新：

- `docs/app/APP_DETAILED_FUNCTION_PROTOTYPE_SPEC.md`：客户和研发都可阅读的详细功能与原型说明。
- `docs/app/APP_PAGE_LEVEL_PRODUCT_DESIGN.md`：继续作为 92 页页面级设计基线。
- `docs/app/assets/page-prototypes/manifest.json`：截图与功能映射的机器可校验清单。
- `docs/app/assets/page-prototypes/mobile/`：移动端默认与关键状态截图。
- `docs/app/assets/page-prototypes/admin/`：后台默认与关键状态截图。

## 4. 单功能确认单元

每个 Page ID 必须包含以下字段：

1. **功能标识**：Page ID、平台、模块、优先级和设计路由。
2. **用户价值**：该功能解决的问题及其对用户或运营的价值。
3. **适用角色**：可以进入、操作和审批的角色。
4. **前置条件**：账号、会员、资料、权限、网络和业务状态要求。
5. **进入路径**：入口页面、深链或后台导航位置。
6. **页面结构**：信息分区、内容层级和固定披露。
7. **详细交互**：主操作、次要操作、返回路径、成功反馈和失败下一步。
8. **业务规则**：服务端判断、幂等、额度、状态机和不可变边界。
9. **页面状态**：正常、加载、空、错误、受限、冲突、只读等实际适用状态。
10. **数据与权限**：读取与写入对象、服务端权限和审计要求。
11. **验收标准**：可执行、可观察且能被测试验证的页面级验收项。
12. **原型图**：与 Page ID、页面名称和状态完全一致的截图。
13. **客户确认**：确认、需修改、暂缓，以及意见和签字空间。

## 5. 原型截图规格

### 5.1 截图来源

唯一截图来源为：

`docs/app/interactive-prototype/pages.html`

页面通过以下参数确定：

```text
pages.html?page={PAGE_ID}&state={STATE}&capture=doc
```

`capture=doc` 只改变文档截图版式，不改变页面业务内容。该模式隐藏页面目录和底部翻页控件，保留：

- Page ID、页面名称、优先级、路由和当前状态。
- 移动端设备或后台工作台的完整页面预览。
- 页面目标、入口、主次操作、必备状态、不可变规则和页面级验收。

### 5.2 画面布局

- 统一画布：1600 × 1000。
- 移动端：左侧放大手机页面，右侧展示页面设计说明。
- 管理后台：左侧展示完整后台工作区，右侧展示页面设计说明。
- 不包含全局页面目录，避免客户误把其他 Page ID 当作当前功能。
- 不使用模糊背景、旅程弹窗或多个功能拼图作为单页功能截图。

### 5.3 文件命名

默认状态：

```text
{page-id}__default.png
```

P0 关键状态：

```text
{page-id}__state-{state-index}.png
```

例如：

```text
app-auth-02__default.png
app-auth-02__state-05.png
adm-wal-04__state-03.png
```

文件名只使用稳定的 Page ID、英文标记和状态序号；中文状态名称保存在映射清单中，避免跨平台文件系统、压缩包和自动化脚本出现编码差异。

### 5.4 P0 关键状态选择

每个 P0 页面补充一个最影响用户决策或业务安全的状态。选择顺序：

1. 无权限、受限、冻结、冲突。
2. 失败、错误、异常、不可用。
3. 到期、下架、额度尽、维护或强制升级。
4. 若无上述状态，选择最重要的处理中或空状态。

状态名称必须来自 `page-catalog.js`，不得为截图临时创造状态。

## 6. 功能与截图的唯一映射

`manifest.json` 中每条截图记录至少包含：

```json
{
  "pageId": "APP-AUTH-02",
  "platform": "mobile",
  "module": "启动与认证",
  "priority": "P0",
  "route": "/auth/login",
  "pageName": "登录",
  "state": "正常",
  "variant": "default",
  "image": "mobile/app-auth-02__default.png",
  "sourceUrl": "pages.html?page=APP-AUTH-02&state=正常&capture=doc"
}
```

DOCX 中的标题、图注、替代文本和正文 Page ID 全部从同一条记录生成。生成器不得通过章节位置猜测截图，也不得人工把旅程截图插入单页功能章节。

## 7. 文档版式

沿用现有 `standard_business_brief` 预设和 `customer_pack` 首页模板，不重新设计品牌风格。

单页功能版式：

- 页首：模块、Page ID、页面名称、状态和优先级。
- 上半页：功能目标、角色、前置条件和交互摘要。
- 中部：默认状态原型图。
- 下半页：业务规则、状态、权限和验收清单。
- P0 关键状态图按两张一页的附录方式集中展示，避免把正文扩展到不可控长度。

预计：

- 客户主文档约 125～160 页。
- 逐页交互确认册约 120～135 页。
- 图片使用适合 Word 阅读的无损 PNG，并按实际版面尺寸压缩，不保存重复原图。

两份 DOCX 均完整覆盖 92 个页面：

- 客户主文档在对应功能章节内放入 92 张默认态原型图，54 张 P0 关键状态图集中放入状态附录，并从正文建立引用。
- 逐页交互确认册以 Page ID 为确认单元，收录相同的 92 张默认态和 54 张 P0 关键状态图。
- 既有跨页面旅程图仅可用于模块总览，不得替代单个功能点对应的页面原型图。

## 8. 生成流程

1. 从 `page-catalog.js` 读取 92 个页面定义。
2. 验证 Page ID 唯一、平台数量为移动端 49 和后台 43。
3. 为每页确定默认状态，为 54 个 P0 页面确定关键状态。
4. 使用本地交互原型逐页生成 146 张截图。
5. 检查截图标题、Page ID、状态、图片加载和横向溢出。
6. 生成 `manifest.json` 和详细功能 Markdown。
7. 根据同一数据源生成两份 DOCX。
8. 运行截图覆盖、功能映射、DOCX 图片数和图注一致性检查。
9. 渲染 DOCX 为逐页 PNG，并检查每一页。
10. 运行无障碍、表格几何、压缩包完整性和构建验证。

## 9. 自动校验

生成失败条件：

- 默认截图数量不是 92。
- P0 关键状态截图数量不是 54。
- 移动端或后台 Page ID 数量不是 49/43。
- 存在重复 Page ID、重复截图或未引用截图。
- 图注中的 Page ID、页面名称或状态与截图不一致。
- 任一功能没有默认截图、详细说明、状态或验收标准。
- 截图中未显示自身 Page ID 和当前状态。
- 图片加载失败、页面存在横向溢出或捕获到动画中间帧。
- DOCX 中存在没有替代文本的图片。
- DOCX 渲染出现裁切、重叠、缺字、孤立标题或图片与图注分页。

## 10. 验收标准

### 10.1 内容覆盖

- 92/92 页面具有完整功能说明和默认原型图。
- 54/54 P0 页面具有关键状态原型图。
- 14 个移动端和后台功能组均有模块说明、页面目录和客户确认区。
- 所有客户确认事项均能追溯到具体章节或 Page ID。

### 10.2 映射准确性

- 正文 Page ID、页面名称、状态、图注、替代文本和图片内容一致率为 100%。
- 不再出现“登录章节展示推荐页”等跨功能错位。
- 每张截图只描述一个 Page ID 和一个明确状态。

### 10.3 文档质量

- DOCX 每页在 100% 缩放下可读。
- 原型图文字、主操作和状态反馈可辨识。
- 不存在图片拉伸、模糊、裁切或跨页错位。
- 表格、标题、页眉页脚、页码和确认栏保持统一。
- 无障碍检查的高、中、低问题均为 0。

### 10.4 交付边界

- 本轮只修改文档、文档原型捕获模式、截图资产和生成/校验脚本。
- 不创建 KMP 项目，不修改 App 业务 API，不新增数据库 migration，不部署生产环境。

## 11. 实施后客户评审顺序

1. 先确认产品边界和五级会员方案。
2. 按模块阅读详细功能说明。
3. 按 Page ID 检查默认原型与关键状态原型。
4. 在逐页确认册记录修改意见。
5. 完成 C-01～C-08、逐功能确认和签字页后，才进入视觉定稿、契约冻结和研发排期。
