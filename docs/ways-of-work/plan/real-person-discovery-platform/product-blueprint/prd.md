## 3. Goal

### Problem

MeiGallery 已拥有真实人物、授权媒体、标签和后台运营能力，但图库模型无法完整表达真人主体、公开资料、消息接收主体、付费权益和未来本人入驻。App 需要在复用现有数据的同时建立清晰、可审计的真人互动模型。

### Solution

建立以 `Person` 和 `PersonProfile` 为内容核心、以 `Account` 为观看者和付费主体的单边真人发现平台。管理员控制真人资料准入和代运营私信；观看者通过推荐、搜索、关注、喜欢、收藏、心享会员私信、礼物和装扮消费形成完整旅程。未来真人本人通过认领流程绑定账号并接管资料和新会话。

### Impact

- 消除普通账号、真人主体和图库内容之间的身份混淆。
- 复用 MeiGallery 真人内容并保留授权和审计证据。
- 建立可解释的心享会员私信和管理员代运营服务。
- 通过五级心享会员、金币、礼物和装扮形成可扩展商业化。
- 为真人本人入驻、桌面端和多地区扩展保留稳定边界。

## 4. User Personas

| Persona | 目标 | 核心权限 |
|---------|------|----------|
| 访客 | 理解产品并决定注册 | 浏览品牌、条款和有限公开内容 |
| 普通观看者 | 发现和保存喜欢的真人 | 浏览、搜索、喜欢、关注、收藏、举报和管理账号 |
| 心享会员 | 获得更深互动和装扮权益 | 普通能力 + 创建私信、等级额度、高级筛选、会员商品 |
| 内容管理员 | 建立可信真人供给 | 上传、导入、认证、发布、暂停和归档真人资料 |
| 代运营管理员 | 处理未认领真人的私信 | 查看被分配会话、以平台身份回复、举报升级和审计 |
| 商业运营/财务 | 管理商品和账本 | 会员、金币、礼物、装扮、订单、退款、调币和对账 |
| 未来入驻真人 | 认领并运营本人资料 | 核验、绑定账号、维护资料、接收认领后的新会话 |

## 5. User Stories

- 作为普通观看者，我想按地区、热度和偏好发现真人，以便快速找到感兴趣的内容。
- 作为普通观看者，我想喜欢、关注和收藏真人，以便继续查看其更新并改善推荐。
- 作为普通观看者，我想清楚知道私信需要会员，以便在购买前理解权益和限制。
- 作为心享会员，我想直接向喜欢的真人资料发起私信，以便获得平台提供的互动服务。
- 作为心享会员，我想知道消息实际由本人还是平台运营接收，以便理解服务真实边界。
- 作为内容管理员，我想只有认证并发布的真人资料进入列表，以便保证供给质量。
- 作为代运营管理员，我想在统一工作台处理分配的会话，以便稳定响应并保留审计。
- 作为商业运营，我想把未来功能配置到不同会员等级，以便不依赖名称硬编码。
- 作为财务人员，我想所有金币变化都来自账本分录，以便完成对账和争议处理。
- 作为未来入驻真人，我想认领资料并控制认领后的新消息，以便逐步从平台代运营切换为本人运营。
- 作为受限用户，我想清楚看到限制原因、申诉和数据权利入口，以便理解下一步。

## 6. Requirements

### Functional Requirements

#### 产品与角色

- **BLP-FR-001**：普通账号不得创建可公开展示的真人资料，也不得进入真人列表。
- **BLP-FR-002**：真人主体、公开资料、图库和登录账号必须独立建模并通过稳定 ID 关联。
- **BLP-FR-003**：系统必须支持管理员、代运营、商业运营、财务、审核员和未来入驻真人的独立角色。

#### 真人供给

- **BLP-FR-004**：真人资料来源至少包括管理员上传、MeiGallery 导入和外部提交后管理员审核。
- **BLP-FR-005**：只有 `verified + published` 的真人资料可以进入推荐、地区、热门、搜索和分类列表。
- **BLP-FR-006**：资料必须记录来源、授权、认证、审核、运营归属和发布历史。

#### 发现与互动

- **BLP-FR-007**：推荐使用地区、标签、职业、风格、热度和观看者行为，但必须提供非个性化入口。
- **BLP-FR-008**：喜欢、关注、收藏和浏览记录为单向互动，不创建双方匹配。
- **BLP-FR-009**：普通用户可以取消喜欢、取消关注、移出收藏和清理本地历史。

#### 私信与代运营

- **BLP-FR-010**：只有有效心享会员可以创建真人私信；各级额度由 entitlement 提供。
- **BLP-FR-011**：未认领真人的消息进入管理员代运营工作台，已认领真人的新消息进入本人收件箱。
- **BLP-FR-012**：私信入口和会话必须披露真实接收主体，不得伪造真人本人回复或已读。
- **BLP-FR-013**：所有会话支持内容过滤、频控、举报、拉黑、静音、关闭和审计。

#### 商业化

- **BLP-FR-014**：首版同时开放心遇、心悦、心知、心契和心耀五级心享会员。
- **BLP-FR-015**：会员使用 rank 和 entitlement 判断，名称、颜色和文案不得成为授权依据。
- **BLP-FR-016**：金币不可提现、转账、兑换法币或跨产品使用。
- **BLP-FR-017**：礼物、头像框、主页皮肤和聊天皮肤使用统一商品目录和库存/有效期模型。
- **BLP-FR-018**：管理员加币、扣币、补偿和冲正必须生成账本分录与审计事件。

#### 未来认领

- **BLP-FR-019**：系统支持真人本人提交认领、身份核验、授权复核、管理员批准和账号绑定。
- **BLP-FR-020**：认领后默认只接管新会话；历史代运营会话按观看者同意和合规规则决定是否交接。

#### 跨平台与迁移

- **BLP-FR-021**：Android/iOS 首发，Windows/macOS 后续；Nuxt Web 和后台继续保留。
- **BLP-FR-022**：现有 MeiGallery 数据按共享核心 + 渐进迁移方式接入，不直接让客户端读取 legacy 表。

### Non-Functional Requirements

- **BLP-NFR-001**：推荐、会员和商品配置必须版本化、可审计、可灰度和可回滚。
- **BLP-NFR-002**：对象级权限由服务端执行，客户端展示状态不构成授权。
- **BLP-NFR-003**：所有管理员写操作写入操作者、目标、原因、前后状态和时间。
- **BLP-NFR-004**：消息、金币和订单写入使用幂等键，重复提交不得重复扣费或生成内容。
- **BLP-NFR-005**：前台支持加载、空、错误、离线、权限不足、安全受限和强制升级状态。
- **BLP-NFR-006**：移动和桌面端支持屏幕阅读器、键盘焦点、动态字体/缩放和高对比度。
- **BLP-NFR-007**：日志不得包含令牌、私信正文、完整身份证件、精确位置或商店凭证明文。
- **BLP-NFR-008**：Kotlin 与 TypeScript 通过版本化 schema 保持契约一致。

## 7. Acceptance Criteria

- **BLP-AC-001**：Given 一个普通观看者账号，When 管理员查询真人列表，Then 该账号永远不作为真人资料出现。
- **BLP-AC-002**：Given 一个未认证或未发布的真人资料，When 前台请求任一列表或搜索，Then 该资料不可见。
- **BLP-AC-003**：Given 观看者喜欢和关注真人，When 对方没有账号，Then 系统只记录单向互动且不创建匹配。
- **BLP-AC-004**：Given 普通观看者点击私信，When 没有有效会员 entitlement，Then 展示心享会员页且不创建会话。
- **BLP-AC-005**：Given 心享会员向未认领真人发起私信，When 会话创建，Then 进入管理员工作台并在用户侧披露平台代运营。
- **BLP-AC-006**：Given 管理员回复消息，When 消息落盘，Then 存在实际操作员审计且前台不显示真人本人回复。
- **BLP-AC-007**：Given 管理员执行加币或扣币，When 操作完成，Then 余额来自新账本分录且用户可查看原因说明。
- **BLP-AC-008**：Given 真人本人完成认领，When 新私信创建，Then 会话路由到本人；历史代运营消息不自动暴露。
- **BLP-AC-009**：Given 会员名称或额度被后台修改，When 客户端刷新目录，Then 已支持的展示和权限变化无需升级 App。
- **BLP-AC-010**：Given 新 entitlement 需要客户端不存在的页面，When 旧客户端读取目录，Then 忽略未知能力并保持可用，服务端不授予不可执行操作。

## 8. Out of Scope

- 普通用户创建公开真人资料。
- 双方喜欢、招呼、匹配和解除匹配。
- 普通用户之间的私信、群聊或随机匿名聊天。
- 管理员在未披露的情况下冒充真人本人。
- 用户提现、金币转账、法币兑换、随机礼物或博彩机制。
- 未经本人和观看者同意自动移交历史私信。
- 首阶段直播、公开评论、音视频通话和用户上传公开媒体。
- 使用 Compose Web 替换 Nuxt Web 或管理后台。
