## 3. Goal

### Problem

观看者希望围绕感兴趣的真人资料发起沟通，但当前资料中的真人尚未本人入驻。平台既不要求双方匹配，也不能让用户误以为平台运营回复来自真人本人。消息还涉及会员资格、新话题额度、多人运营、内容审核、断线恢复、举报拉黑和隐私证据；如果只设计一个聊天页面，无法形成可上线的运营闭环。

### Solution

为持有有效 `direct_message.create` entitlement 的会员提供“发起话题”能力，不要求目标同意、互相关注或匹配。App 1.0 所有未认领真人采用 `platform_managed` 模式，用户界面持续披露“话题由平台运营接收与处理”。服务端内部仍以 Conversation、Message 和 `direct_message.*` 作为稳定领域/API 标识，维护会话顺序、资格、内容状态和实际操作员；Nuxt 工作台提供队列、分配、交接、内部备注和安全升级。未来只有在真人完成认领且版本明确开放后，用户界面才可切换为“给本人发消息”。

### Impact

- 完成“发现真人 → 会员门槛 → 发起话题 → 平台运营处理”的 1.0 核心闭环。
- 在不冒充真人的前提下，让现阶段供给可以被稳定运营。
- 用统一会话模型支持未来本人认领后的新会话路由，不泄露历史代运营消息。
- 建立可恢复、可审核、可追责的消息基础，为后续经评审的媒体消息留出边界。

## 4. User Personas

| Persona | 目标 | 约束与关注点 |
|---------|------|--------------|
| 普通观看者 | 了解话题门槛和接收主体 | 无 entitlement 时不能创建空会话，可提交会员申请 |
| 心享会员 | 围绕真人资料发起并持续使用平台话题 | 受额度、频控、拉黑和安全状态约束 |
| 代运营人员 | 以平台身份接收、回复和交接会话 | 不得冒充真人，内部备注不得外泄 |
| 运营组长 | 管理队列、班次、负载、SLA 和质量 | 不能绕过会话安全冻结 |
| 安全审核人员 | 处理命中规则、举报和高危内容 | 只访问案件必要证据 |
| 客服/审计人员 | 解释状态并还原操作历史 | 私信正文访问必须有授权和目的 |
| 未来认领真人 | 在认领后接收新的会话 | App 1.0 不开放；历史会话默认隔离 |

## 5. User Stories

- 作为普通观看者，我想在点击“发起话题”时先看到会员条件、平台接收说明和限制，并可提交会员申请，以免产生错误预期。
- 作为会员，我想不经双方同意或匹配直接发起话题，以便使用已获得的会员权益。
- 作为会员，我想在详情、会话列表和会话页持续看见实际接收主体，以便知道谁会阅读和回复。
- 作为会员，我想在网络中断或重复点击后仍只发送一条消息，以免产生重复内容。
- 作为会员，我想看到发送中、审核中、已发送、已读、失败和已撤回状态，以便理解消息进度。
- 作为会员，我想静音、关闭、举报或拉黑，以便控制不需要或不安全的互动。
- 作为代运营人员，我想从待分配队列领取会话并看到必要上下文，以便高效而合规地回复。
- 作为运营组长，我想按地区、语言、真人、班次和负载分配会话，以便管理服务容量。
- 作为安全审核人员，我想冻结高危会话并只读取必要证据，以便处置风险。
- 作为审计人员，我想知道每条平台消息由谁实际发送，以便调查冒充或越权问题。

## 6. Requirements

### 6.1 Functional Requirements

#### 入口、门槛与建会话

- **MOP-FR-001**：真人详情的用户可见入口统一命名为“发起话题”，必须由服务端返回 `operationMode`、接收主体标签、可用状态和所需 entitlement；客户端不得自行推断真人是否本人接收，也不得在 `platform_managed` 模式显示“给 TA 私信”。
- **MOP-FR-002**：普通观看者点击“发起话题”时展示会员权益、获取方式、平台接收主体、额度和不保证回复说明，可进入会员申请流程，但不调用创建会话写接口。
- **MOP-FR-003**：有效会员创建会话不要求目标真人同意、双方喜欢、互相关注或匹配；任何 consent 字段都不得成为 App 1.0 建会话条件。
- **MOP-FR-004**：服务端创建前必须校验账号/设备安全、`direct_message.create`、新会话额度、真人 `verified + published`、运营模式、拉黑关系、频控和审核限制。
- **MOP-FR-005**：同一观看者与同一真人默认只有一条未关闭有效会话；按观看者 + 真人建立唯一约束，重复幂等请求返回既有会话且不重复消耗额度。
- **MOP-FR-006**：建会话成功响应必须包含会话 ID、接收模式、披露版本、新会话剩余额度、重置时间和当前安全状态。
- **MOP-FR-007**：App 1.0 中所有未认领真人的新会话固定为 `platform_managed`；本人接收能力属于 M3，不能通过后台开关在 1.0 客户端静默启用。
- **MOP-FR-008**：资料暂停、授权撤回、账号受限或拉黑后禁止创建新会话；旧入口必须返回当前不可用原因而不是空白页。

#### 接收主体披露

- **MOP-FR-009**：“话题由平台运营接收与处理”必须出现在详情话题入口附近、首次创建确认、会话列表标签、会话顶部和不可删除的首条服务说明卡中；主按钮不得仅显示“私信”或“聊天”。
- **MOP-FR-010**：平台回复统一使用平台标识和 `senderType=platform_operator`；可显示经批准的服务昵称，但不得使用真人头像、真人签名或第一人称设定暗示本人回复。
- **MOP-FR-011**：平台运营会话不得发送或展示真人在线、真人正在输入、真人已读、实时位置或“她正在等你”等推断状态。
- **MOP-FR-012**：已读只表示当前实际接收主体已查看到某 sequence；在 App 1.0 中用户文案为“平台运营已读”，不得缩写为“对方已读”。
- **MOP-FR-013**：运营模式变化必须写入不可删除系统消息并刷新全端标签；未来认领不把历史会话自动交给真人，历史交接审批也不影响会员直接创建新会话的规则。

#### 会话和消息状态

- **MOP-FR-014**：用户侧会话状态至少包括 `active`、`restricted`、`closed`；工作台队列状态至少包括 `unassigned`、`assigned`、`awaiting_operator`、`awaiting_viewer`、`safety_review`、`closed`。
- **MOP-FR-015**：App 1.0 用户消息类型只支持文本和表情；系统消息只能由服务端生成，图片、语音、视频、文件、位置和通话入口不得显示。
- **MOP-FR-016**：每条客户端消息包含稳定 `clientMessageId`；服务端分配单调递增 sequence，并以会话 + `clientMessageId` 保证幂等。
- **MOP-FR-017**：消息状态至少包括本地待发送、服务端审核中、已接受、已送达、已读、发送失败、已拒绝和已撤回；客户端不得在服务端确认前显示已送达或已读。
- **MOP-FR-018**：文本发送必须依次通过有效 `direct_message.send`、会话权限、内容格式、长度、频控和内容安全检查；需人工审核的消息进入 `review_pending`，不向接收队列伪装为正常已送达。
- **MOP-FR-019**：用户可在服务端返回的 `recallUntil` 之前申请撤回本人消息；撤回仅替换用户侧内容为占位状态，原始证据按批准的安全保留策略隔离保存，不允许编辑消息。
- **MOP-FR-020**：失败消息允许以原 `clientMessageId` 重试；内容被拒绝、会话受限或窗口过期时给出明确原因和可用下一步。
- **MOP-FR-021**：静音只停止站内消息提醒，不改变消息收取；关闭会话停止双方新消息，重新开启需要服务端策略允许，不能因解除拉黑自动恢复。

#### 实时、补拉与多设备

- **MOP-FR-022**：客户端通过 HTTP 获取短期实时 ticket 后连接会话 Durable Object；实时事件只作为增量，HTTP 会话/消息 API 是断线恢复的权威补拉入口。
- **MOP-FR-023**：连接 `hello` 携带最后确认 sequence，服务端补发缺失事件；发现 gap、ticket 失效或 schema 不支持时停止直接应用并触发 HTTP 补拉。
- **MOP-FR-024**：多设备已读以账号和实际接收主体的最高 sequence 合并；旧设备重连不得把已读状态回退。
- **MOP-FR-025**：会员到期不删除既有会话和历史，但立即失去 `direct_message.send`，既有会话转为只读；新会员 grant 生效后仍需服务端重新校验会话安全状态，不能凭旧页面缓存继续发送。
- **MOP-FR-026**：拉黑、账号冻结、资料暂停和会话安全冻结发生时，实时层立即撤销写权限并推送受限事件；在途请求按服务端最终状态判定。

#### 代运营队列与分配

- **MOP-FR-027**：新 `platform_managed` 会话进入待分配队列，系统可按真人、地区、语言、班次、运营组、优先级和当前负载建议分配。
- **MOP-FR-028**：代运营人员只能查看被分配给本人或所属组的会话；跨组查看、敏感会话访问和批量检索需要额外权限并记录审计。
- **MOP-FR-029**：领取、转派、协作、退回队列和交班使用版本号/租约防止多人同时回复；并发冲突时强制刷新最新 assignment。
- **MOP-FR-030**：工作台会话上下文只展示公开真人资料、会员服务摘要、用户消息、必要账号风险提示和已有处置；不得显示不相关的完整身份、钱包或隐私数据。
- **MOP-FR-031**：内部备注与用户消息使用独立资源和权限；任何用户 API、实时事件、导出或消息摘要不得返回内部备注。
- **MOP-FR-032**：快捷话术必须经过版本化审核，操作员确认后才能发送；发送后仍记录实际操作员，不允许机器人自动伪装成人工或真人。
- **MOP-FR-033**：建议基线为每日 10:00—22:00 提供平台运营服务、90% 首次响应在 1 个服务日内完成；在 OQ-010 关闭前均为待客户确认值。工作台显示等待时长、目标响应时间和服务时段，用户侧只展示当前生效配置并明确“不保证固定回复时间”；SLA 逾期触发内部提醒或升级，不生成虚假回复。
- **MOP-FR-034**：会话可以升级至安全审核、客服或组长；安全冻结优先于运营回复，只有授权审核结果可以解除。

#### 安全、用户控制与证据

- **MOP-FR-035**：用户可从会话举报真人、会话或指定消息；举报成功后可继续选择拉黑，系统保留举报时最小证据快照。
- **MOP-FR-036**：拉黑后阻止双方新消息、从推荐移除目标并关闭/限制会话；管理员不得以代运营权限绕过用户拉黑继续发送。
- **MOP-FR-037**：高危关键词、骚扰、诈骗、违法或自伤风险按安全策略进入审核/升级；具体策略与处置以 A-07 PRD 为准。
- **MOP-FR-038**：消息正文不得进入通用日志、分析、错误追踪或运营看板；审计仅保存内容引用、哈希、状态和必要证据访问记录。
- **MOP-FR-039**：用户前台删除会话仅隐藏本人列表；安全、申诉和法定保留中的数据按 OQ-020 隔离，不承诺物理立即删除。

#### 通知、分析与质量

- **MOP-FR-040**：新平台回复、审核结果、会话受限和接收主体变化生成站内通知；App 1.0 不依赖 APNs/FCM。
- **MOP-FR-041**：至少记录私信门槛曝光、建会话请求/成功/失败、首条消息、有效往返、状态变化、披露说明展开、静音、关闭、举报和拉黑事件。
- **MOP-FR-042**：工作台统计队列量、等待时长、首次响应、有效往返、转派、关闭、审核升级、举报和披露投诉；不得以个人消息量公开排名操作员或用户。
- **MOP-FR-043**：抽检能够关联披露版本、平台消息、实际操作员、话术版本和审核结果，但正文访问需单独授权并留下理由。
- **MOP-FR-044**：容量建议基线为每名一线运营每服务日最多处理 30 个新增首次响应、个人待处理上限 20 个；平台队列达到 70%/85%/100% 时，依次触发内部预警、减少新入口曝光/收紧新话题额度、暂停创建新话题并保留既有会话。阈值、动作和恢复条件必须服务端配置，正式上线值需在 OQ-035 关闭后冻结。
- **MOP-FR-045**：操作员回复必须围绕平台服务、公开资料、活动说明和安全帮助，不得承诺真人本人已阅读、线下见面、关系结果、返现收益或代替真人作出身份/情感表态；越界话术应被拦截或升级复核。

### 6.2 主流程

#### 会员发起并使用平台话题

```text
真人详情点击“发起话题”
→ 展示平台接收说明并请求服务端校验
→ 校验会员、额度、真人状态、拉黑、频控和安全
→ 创建或复用唯一有效会话
→ 写入不可删除服务说明卡
→ 用户发送文本/表情
→ 服务端幂等写入、审核、排序
→ 平台工作台接收并以运营身份回复
→ 客户端实时接收；断线后按 sequence 补拉
```

#### 代运营处理会话

```text
新会话进入待分配队列
→ 系统建议分组/操作员
→ 操作员领取并获得会话租约
→ 查看最小必要上下文和披露状态
→ 回复 / 添加隔离内部备注 / 升级安全审核
→ 更新等待状态和服务指标
→ 转派、交班或关闭
→ 所有动作写入审计
```

### 6.3 权限矩阵

| 动作 | 观看者 | 有效会员 | 被分配操作员 | 运营组长 | 安全审核 | 审计 |
|------|--------|----------|----------------|----------|----------|------|
| 查看本人会话 | 已有会话 | 是 | 否 | 否 | 按案件 | 受控 |
| 创建新会话 | 否 | entitlement 允许 | 否 | 否 | 否 | 否 |
| 发送用户消息 | 按会话 entitlement | 按会话 entitlement | 否 | 否 | 否 | 否 |
| 平台身份回复 | 否 | 否 | 被分配范围 | 授权范围 | 否 | 否 |
| 查看/写内部备注 | 否 | 否 | 被分配范围 | 授权范围 | 案件范围 | 只读审计 |
| 转派和队列管理 | 否 | 否 | 退回/申请转派 | 是 | 冻结优先 | 否 |
| 查看消息正文 | 本人可见部分 | 本人可见部分 | 被分配范围 | 业务必要范围 | 案件必要范围 | 需专项授权 |
| 删除消息/审计 | 否 | 否 | 否 | 否 | 否 | 否 |

### 6.4 异常与恢复矩阵

| 场景 | 前台表现 | 工作台/服务端行为 | 恢复方式 |
|------|----------|-------------------|----------|
| 无会员/额度耗尽 | 不创建会话，显示资格或重置时间 | 不写会话、不耗额度 | grant 生效或周期重置 |
| 资料刚被暂停 | 显示资料不可用 | 拒绝新会话并撤销实时写权限 | 资料恢复并重新校验 |
| 重复发送 | 保留一条消息 | 由 `clientMessageId` 返回原结果 | 无需人工处理 |
| 文本待人工审核 | 显示审核中 | 不进入正常运营队列 | 审核通过/拒绝后更新 |
| 实时连接中断 | 显示离线横幅，可排队本地草稿 | HTTP 仍提供权威读取/提交 | 重连后按 sequence 补拉 |
| 多人同时领取 | 后领取者看到冲突 | 租约/版本校验拒绝覆盖 | 刷新并选择其他会话 |
| 用户拉黑 | 会话变为受限 | 停止平台发送和推荐 | 解除后仍不自动重开 |
| 安全冻结 | 输入区替换为状态说明 | 只允许安全角色处置 | 审核结论解除或关闭 |
| 内部备注误投消息通道 | 服务端拒绝 | 生成高优先级审计告警 | 安全复盘，不自动重试 |
| 队列达到容量阈值 | 展示预计处理说明，必要时暂停新话题 | 依 70%/85%/100% 配置逐级降级并保留既有会话 | 扩容或积压回落后按审核流程恢复 |

### 6.5 Non-Functional Requirements

- **MOP-NFR-001**：同一会话消息顺序由服务端权威 sequence 决定；重试、乱序和 Durable Object 休眠不得造成重复或倒序展示。
- **MOP-NFR-002**：消息创建、会话复用、额度消耗、通知生成和工作台状态更新具备幂等及可恢复语义。
- **MOP-NFR-003**：实时 ticket 短期有效、绑定账号/会话/设备权限；撤权后旧 ticket 和现有连接不能继续写入。
- **MOP-NFR-004**：消息正文、内部备注和审核证据分级加密/隔离，不进入通用日志、分析或崩溃报告。
- **MOP-NFR-005**：用户会话支持加载、空、离线、补拉、审核中、失败、下架、拉黑、账号受限和升级客户端状态。
- **MOP-NFR-006**：移动端会话支持动态字体、屏幕阅读器和减少动态效果；管理工作台支持完整键盘导航、可见焦点和长文本缩放。
- **MOP-NFR-007**：消息延迟、重复率、sequence gap、队列积压、未分配超时、身份异常和内部备注泄漏具备 SLO、告警和 Runbook。
- **MOP-NFR-008**：消息 schema 向前兼容；未知消息类型不执行、不自动下载，显示安全占位并提示升级。

## 7. Acceptance Criteria

- **MOP-AC-001**：Given 普通观看者点击“发起话题”，When 无 `direct_message.create`，Then 展示会员、会员申请入口和平台接收说明，不创建会话且不消耗额度。
- **MOP-AC-002**：Given 有效会员未喜欢或关注目标真人，When 服务端校验通过，Then 可直接创建会话，不要求任何双方同意或匹配状态。
- **MOP-AC-003**：Given 同一会员对同一真人重复建会话，When 请求重试或幂等键重复，Then 返回同一有效会话并只消耗一次新会话额度。
- **MOP-AC-004**：Given 目标真人未认领，When 用户查看详情、列表和会话页，Then 三处均持续显示平台运营接收/回复，平台消息不使用真人发送身份。
- **MOP-AC-005**：Given 操作员发送平台回复，When 消息落库，Then 用户看到 `platform_operator`，后台能追溯实际操作员，且无法把 sender 改成 `person`。
- **MOP-AC-006**：Given 客户端断线后错过多条事件，When 携带最后 sequence 重连，Then 缺失消息按顺序补齐且不重复。
- **MOP-AC-007**：Given 同一消息因超时重试，When `clientMessageId` 相同，Then 服务端返回原结果并只生成一条通知。
- **MOP-AC-008**：Given 用户拉黑真人，When 操作生效，Then 新消息、平台回复和新会话均被阻止，解除拉黑不自动重开会话。
- **MOP-AC-009**：Given 操作员尝试把内部备注写入用户消息接口，When 提交，Then 服务端拒绝并产生安全审计告警。
- **MOP-AC-010**：Given 会话进入安全冻结，When 普通操作员或会员发送，Then 输入被阻止；只有授权安全结论可解除。
- **MOP-AC-011**：Given 用户在撤回窗口内撤回本人消息，When 服务端确认，Then 全端显示撤回占位，原始证据不出现在普通查询中且审计可追溯。
- **MOP-AC-012**：Given 会员到期仍停留在会话页，When 再次发送，Then 服务端因缺少 `direct_message.send` 拒绝，会话历史保持只读且不因旧页面缓存扩大权限。
- **MOP-AC-013**：Given 新话题队列达到 70%/85%/100% 容量阈值，When 用户尝试发起话题，Then 服务端按当前级别返回明确的正常、限流或暂停结果，既有会话仍可按安全策略读取和处理，且每次升降级均有审计记录。
- **MOP-AC-014**：Given 操作员尝试发送暗示真人本人已读、承诺见面或关系结果的话术，When 提交，Then 规则拦截或进入组长复核，用户侧不得收到该越界内容。

## 8. Out of Scope

- 普通观看者创建新私信、用户之间聊天、群聊、随机聊天和匿名聊天。
- 双方同意、互相喜欢、匹配或“配对成功”流程。
- App 1.0 真人本人收件箱、本人在线/输入状态和历史会话交接。
- 图片、语音、视频、文件、实时位置、音视频通话、直播和公开评论。
- 自动生成平台回复、无人确认的话术发送或任何未披露的真人模仿。
- 保证真人本人看到消息、保证回复时长、保证线下见面或关系结果。
- 操作员查看未分配/无业务目的的私信正文，或批量导出消息。
- 编辑已发送消息、物理删除审计证据或通过解除拉黑自动恢复会话。
