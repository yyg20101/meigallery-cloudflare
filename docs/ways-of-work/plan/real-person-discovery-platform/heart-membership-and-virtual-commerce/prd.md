# 1. Feature Name

心享会员、金币、礼物与个性装扮

App 版本：1.0

状态：需求讨论中

- 上游蓝图：[真人发现与互动平台产品蓝图](../product-blueprint/prd.md)
- 商业化基线：[商业化与账本设计](../../../../app/MONETIZATION_AND_LEDGER.md)
- 技术架构：[共享平台技术架构](../../../../app/TECHNICAL_ARCHITECTURE.md)

App 1.0 可验收细节分别以 [心享会员、Entitlement 与管理员手动发放](../membership-entitlements-and-manual-grants/prd.md) 和 [金币钱包、追加式账本与管理员调币](../wallet-ledger-and-admin-coin-adjustments/prd.md) 为准；本文继续承担长期商业化边界。

## 3. Goal

### Problem

产品需要支持心享会员平台话题、未来能力分级、礼物打赏、头像框和皮肤购买，同时避免把会员名称硬编码为权限、避免每次运营调整都强制升级 App。金币还必须支持管理员加币和扣币，但任何余额变化都需要可解释、可复核、可对账。

### Solution

建立“心享会员”五级体系，以数值 `rank` 和配置化 entitlement 作为唯一授权依据；App 1.0 同时展示并支持管理员发放心遇、心悦、心知、心契和心耀。五级均具备基础平台话题 entitlement，额度和附加权益由服务端配置。金币采用不可提现的闭环虚拟货币和追加式账本；未来礼物、头像框、主页皮肤和聊天皮肤使用统一商品目录、订单和库存模型。

### Impact

- 用清晰、可长期扩展的五级会员品牌承接平台话题和未来权益。
- 通过 entitlement 解耦等级名称、价格、额度和客户端实现。
- 用礼物与装扮丰富非提现型商业化场景。
- 使管理员调币具备原因、证据、审批、冲正和用户明细。
- 降低配置调整导致 App 强制升级的频率，同时保证未知能力安全降级。

## 4. User Personas

| Persona | 目标 | 核心关注点 |
|---------|------|------------|
| 普通观看者 | 理解各级会员并选择是否申请开通 | 权益、期限、获取方式和限制必须透明 |
| 心享会员 | 使用平台话题、筛选和收藏权益 | 等级状态、额度和到期结果可预期 |
| 商业运营 | 配置会员并手动发放 | 可定时发布目录、设置有效期、灰度和回滚 |
| 财务人员 | 调币、复核和处理争议 | 余额必须由账本推导，操作可审计 |
| 客服/审核人员 | 处理会员和金币异常 | 最小权限查看必要证据 |
| 开发与发布人员 | 安全兼容新增配置 | 旧客户端忽略未知能力，不错误授权 |

## 5. User Stories

- 作为普通观看者，我想一次看到全部五个会员等级，以便比较权益并了解获取方式。
- 作为普通观看者，我想看到平台话题实际接收主体和等级额度，以便提交会员申请前理解服务边界。
- 作为会员，我想查看当前等级、有效期、剩余额度和下一等级新增权益，以便决定是否升级。
- 作为会员，我想在更换设备后从服务端恢复权益，以便继续使用有效会员。
- 作为用户，我想查看金币余额和每一笔管理员调整原因，以便核对余额。
- 作为运营，我想调整名称、文案和额度并手动发放会员，以便在没有在线支付时运营首版。
- 作为财务人员，我想通过追加分录进行加币、扣币、补偿和冲正，以便账实一致。
- 作为审核人员，我想高风险调币需要复核，以便降低误操作和内部滥用。

## 6. Requirements

### Functional Requirements

#### 品牌、等级与公开文案

- **HMC-FR-001**：会员总品牌统一为“心享会员”，首版同时展示并开放五个等级，不使用“VIP/SVIP”作为面向用户的正式等级名称。
- **HMC-FR-002**：五级默认展示定义如下；运营可通过版本化配置调整副文案、视觉、价格和 entitlement，但不得复用 rank 表达不同强弱顺序。

| rank | 等级 | 核心文案 | 默认定位 |
|-----:|------|----------|----------|
| 10 | 心遇 | 从遇见开始，解锁平台话题 | 入门互动 |
| 20 | 心悦 | 看见更多喜欢，发现更加从容 | 进阶发现 |
| 30 | 心知 | 更懂你的偏好，互动更进一步 | 深度体验 |
| 40 | 心契 | 享受高阶服务与专属装扮 | 高阶服务 |
| 50 | 心耀 | 心享至高等级，汇集完整权益 | 旗舰权益 |

- **HMC-FR-003**：会员比较和授权只使用 `rank` 与 entitlement；名称、颜色、图标、价格和营销文案不得参与权限判断。
- **HMC-FR-004**：高等级默认继承低等级权益；个别不继承项必须在目录中显式配置、展示原因并通过产品/合规审批。
- **HMC-FR-005**：App 1.0 会员页必须同时展示当前等级、有效期、获取方式、核心权益、具体额度、不可用能力、服务说明和条款入口，不允许以“更多特权”等模糊文案替代实际内容；价格和续订只在未来在线购买启用后展示。

#### Entitlement 权限目录

- **HMC-FR-006**：entitlement 至少支持布尔、数值额度、枚举档位、集合、时间窗口和按周期重置六类值。
- **HMC-FR-007**：App 1.0 权限目录至少覆盖：创建和发送平台话题、每日新会话额度、高级筛选档位、保存筛选数量、浏览历史保留、收藏文件夹数量、徽章动画、客服优先级和新功能优先体验；赠币、礼物和装扮 entitlement 作为未来字段，不在 1.0 下发可执行值。
- **HMC-FR-043**：心遇至心耀五级有效会员均必须解析出 `direct_message.create=true` 和 `direct_message.send=true`；等级差异通过额度和其他 entitlement 表达。
- **HMC-FR-008**：服务端返回已解析 entitlement 快照、目录版本、来源和有效期；每个受限 API 在服务端重新校验，不信任客户端缓存。
- **HMC-FR-009**：目录支持生效时间、失效时间、灰度范围、最低客户端版本、回滚版本和变更审计。
- **HMC-FR-010**：旧客户端遇到未知 entitlement 时必须忽略展示且不得自行推断授权；服务端不得向不支持该能力的客户端发放不可执行操作。
- **HMC-FR-011**：修改现有字段的名称、排序、文案、价格、额度、可见性和资源，在客户端已有通用渲染能力时无需升级 App；新增页面、原生能力或全新交互仍需发版。

#### 未来商业化：购买、升级、续订与到期

- **HMC-FR-012**：移动端数字会员和金币购买必须使用目标应用商店允许的支付与凭证验证流程；订单最终状态由服务端验证结果决定。
- **HMC-FR-013**：订单状态至少包括已创建、待支付、验证中、已生效、失败、已取消、已退款、已撤销和争议中。
- **HMC-FR-014**：商店回调、客户端补单和恢复购买必须幂等；同一交易凭证不得重复发放会员、金币或商品。
- **HMC-FR-015**：会员支持购买、续订、升级、降级预约、到期、退款撤销和管理员授予；具体叠加/折算规则由商品目录明确展示并版本化。
- **HMC-FR-016**：升级生效后立即刷新 entitlement；降级默认在当前周期结束后生效；到期后自动回落到免费权限，不删除已产生的合法内容和账本记录。
- **HMC-FR-017**：购买前必须明确说明会员不保证真人本人回复、不保证回复时效、不保证线下关系结果，未认领真人的消息由平台运营接收。
- **HMC-FR-018**：会员页不得使用虚假倒计时、默认勾选、隐藏续订条件、难以发现的取消路径或其他误导性设计。

#### 金币钱包与未来充值

- **HMC-FR-019**：金币是平台内闭环虚拟货币；App 1.0 只支持管理员调整和用户明细，未来可购买目录允许的礼物和装扮；始终不可提现、转账、兑换法币、跨产品交易或用于随机博彩。
- **HMC-FR-020**：用户余额由不可变账本分录汇总或可校验快照得出，不允许管理员直接覆盖余额字段。
- **HMC-FR-021**：每笔金币分录必须包含分录 ID、账号、方向、数量、业务类型、业务单号、原因代码、用户可见说明、创建时间和余额结果；管理员操作还需包含操作者和审计关联。
- **HMC-FR-022**：用户金币明细按充值、会员赠送、活动赠送、礼物消费、装扮消费、管理员调整、退款和冲正分类，支持时间筛选和订单关联。
- **HMC-FR-023**：金币扣减必须具备原子性和幂等性；余额不足、商品下架、资源不可用或风控拒绝时不得产生部分扣款。
- **HMC-FR-024**：退款或撤销通过反向分录完成，不修改或删除原分录；若关联金币已消费，按平台规则进入负余额、权益回收或人工处理流程并向用户说明。

#### 管理员加币、扣币与复核

- **HMC-FR-025**：后台允许授权角色发起加币、扣币、补偿和冲正，不区分普通用户或会员，但必须校验账号状态和操作权限。
- **HMC-FR-026**：调币发起人必须选择标准原因代码并填写用户可见说明；内部备注、工单号和证据附件按场景要求记录。
- **HMC-FR-027**：超过配置阈值、短期高频、跨批次或可能导致负余额的操作必须进入双人复核，发起人与复核人不得相同。
- **HMC-FR-028**：扣币不得静默发生。操作生效后通过站内通知告知用户变动数量、原因、时间和申诉入口；内部风控细节可按安全要求隐藏。
- **HMC-FR-029**：任何调币都只能新增账本分录；错误操作使用冲正分录修复，不允许编辑或删除历史记录。
- **HMC-FR-030**：批量调币必须使用任务模型，支持总量预览、抽样复核、幂等键、逐项结果和暂停，不因单个账号失败而重复发放其他账号。

#### 未来商业化：礼物、头像框与皮肤

- **HMC-FR-031**：礼物、头像框、主页皮肤和聊天皮肤使用统一商品目录，至少包含商品类型、名称、说明、资源版本、金币价格、会员门槛、可售时间、上下架状态和退款规则。
- **HMC-FR-032**：礼物是对指定真人资料的非提现型互动表达；接收方不获得可兑换收入、金币余额或分成，不形成线下服务承诺。
- **HMC-FR-033**：赠礼前展示目标真人、礼物、数量、总价和余额；确认后原子扣币并创建礼物记录，重复请求不得重复扣款。
- **HMC-FR-034**：赠礼结果可出现在会话和用户互动明细中，但必须标注接收模式；平台代运营不得将礼物描述为真人本人已接受或感谢，除非确有本人行为证据。
- **HMC-FR-035**：装扮库存支持永久、固定到期日和领取后有效天数三类期限；到期后自动卸下，历史订单和账本保留。
- **HMC-FR-036**：同一槽位只能启用一个装扮；用户可预览、装备、卸下和恢复默认，资源下载失败时回退到默认视觉。
- **HMC-FR-037**：会员专属商品在购买和使用时均校验 entitlement；会员到期后的处理方式必须在商品页明确标注为继续持有、暂停使用或到期失效。
- **HMC-FR-038**：商品下架后不得新购；已购永久装扮原则上继续可用，涉及安全、版权或合规撤回时可禁用并提供通知和适当补偿流程。

#### 展示、通知与指标

- **HMC-FR-039**：会员入口在“我的”、平台话题门槛、高级筛选、权益不足和未来商品会员门槛等场景使用同一服务端目录，避免权益描述不一致。
- **HMC-FR-040**：App 1.0 用户可查看会员变更、金币变动和系统安全站内通知；订单、赠礼、装扮到期和系统推送在对应能力启用后加入。
- **HMC-FR-041**：App 1.0 指标至少包括会员页曝光、等级比较、管理员发放、到期、金币调币和冲正；未来增加购买、支付、恢复购买、充值、消费、退款、礼物和装扮指标，财务报表与产品分析事件分离。
- **HMC-FR-042**：不得公开展示按消费额排名的用户榜、礼物收益榜或诱导攀比的实时榜单。

### Non-Functional Requirements

- **HMC-NFR-001**：订单、账本、库存和 entitlement 发放使用事务或可证明一致的 Saga，任一重试都不得重复发货或扣币。
- **HMC-NFR-002**：账本分录和关键审计日志不可原地修改；修复通过关联冲正记录完成。
- **HMC-NFR-003**：商店凭证只在服务端验证，日志不得包含完整凭证、支付令牌或个人支付信息。
- **HMC-NFR-004**：目录配置必须经过 schema 校验、预览、审批、定时发布和一键回滚，客户端保留最后可用版本。
- **HMC-NFR-005**：所有金额、金币数量、周期和时区使用明确的整数最小单位与服务端时间，避免浮点和客户端时钟导致差异。
- **HMC-NFR-006**：高风险后台操作启用强认证、最小权限、频控、异常告警和双人复核。
- **HMC-NFR-007**：会员表格、价格、倒计时、余额、购买和装扮控件支持屏幕阅读器、动态字体、键盘操作和减少动态效果。
- **HMC-NFR-008**：客户端离线时可查看最近一次成功同步的会员和库存，但不得离线完成购买、扣币、赠礼或调币。

## 7. Acceptance Criteria

- **HMC-AC-001**：Given App 1.0 会员页，When 普通观看者打开，Then 同时显示心遇至心耀五级名称、文案、获取方式、期限、具体权益和接收主体说明，且没有在线支付入口。
- **HMC-AC-002**：Given 运营修改心悦的展示文案和每日新会话额度，When 配置发布且客户端支持对应字段，Then 无需升级 App 即可更新展示和服务端权限。
- **HMC-AC-003**：Given 旧客户端收到未知 entitlement，When 渲染会员页，Then 忽略未知展示且不会错误获得权限或崩溃。
- **HMC-AC-004**：Given 管理员重复提交同一会员发放请求，When 幂等键相同，Then 只生成一份有效 grant；商店凭证验收延后到未来商业化阶段。
- **HMC-AC-005**：Given 会员到期，When 再次创建平台话题，Then 服务端拒绝并引导查看会员申请状态、重新提交申请或联系平台；既有会话和账本记录不被删除。
- **HMC-AC-006**：Given App 1.0 用户打开钱包，When 查看可执行操作，Then 只能查看余额和明细，不显示充值、礼物或装扮购买入口。
- **HMC-AC-007**：Given 服务端下发未来礼物或装扮配置，When App 1.0 客户端不支持对应 capability，Then 安全忽略且不产生扣币操作。
- **HMC-AC-008**：Given 管理员执行低风险加币，When 操作成功，Then 生成包含原因和操作者的账本分录，用户收到可读明细与通知。
- **HMC-AC-009**：Given 管理员发起超过阈值的扣币，When 未经第二人复核，Then 余额保持不变；复核通过后生成新分录且原申请可追溯。
- **HMC-AC-010**：Given 一笔错误扣币已生效，When 财务执行冲正，Then 原记录保持不变，新增反向分录并恢复正确余额。
- **HMC-AC-011**：未来永久头像框版权撤回和补偿验收在装扮 Feature 启用前执行，不作为 App 1.0 发布门禁。
- **HMC-AC-012**：未来赠礼离线保护验收在礼物 Feature 启用前执行，不作为 App 1.0 发布门禁。

## 8. Out of Scope

- 会员保证真人本人回复、保证回复时间或保证建立关系。
- 金币提现、用户间转账、兑换法币、跨产品流通和二级交易市场。
- 真人通过礼物获得收益、分成或可提现余额。
- 盲盒、抽奖、概率礼物、博彩或以高消费触发不透明权益。
- 公开消费榜、送礼榜或以消费金额决定真人认证与推荐真实性。
- 使用会员等级绕过举报、拉黑、内容审核、年龄、隐私或合规限制。
- 通过远程配置下载和执行任意代码，或在旧客户端强行启用尚未实现的新页面/原生能力。
- 首版家庭共享、跨平台会员迁移、会员赠送和用户间商品转赠。
- App 1.0 在线支付、金币充值、礼物和装扮交易；这些能力的长期要求保留在本文，启用时另行形成发布范围和客户端版本门槛。
