## 3. Goal

### Problem

App 1.0 暂不允许用户充值或消费金币，但业务需要管理员为指定账号加币、扣币、补偿和纠错，并让用户看到余额与明细。如果后台直接修改余额、删除错误记录或只写模糊备注，将无法解释金额来源，也无法发现重复操作、越权调币、负余额和批量任务部分失败。

### Solution

建立仅追加的金币账本：任何余额变化都必须由不可编辑的分录产生，余额是分录汇总和受控快照的权威结果。管理员通过“申请 → 风险判断 → 必要复核 → 原子入账 → 站内通知”的流程执行调币；错误不改历史，只创建关联冲正。用户端只展示余额、明细、规则和申诉入口，不展示充值、提现、转账、赠礼或消费按钮。

### Impact

- 满足管理员加币、扣币和补偿需求，同时保留完整原因与责任链。
- 用户可以理解每次变动，客服可以按业务单号定位争议。
- 高风险和批量操作具备职责分离、幂等、部分结果和对账机制。
- 为后续礼物和装扮复用账本基础，但 App 1.0 不提前开放交易能力。

## 4. User Personas

| Persona | 目标 | 约束与关注点 |
|---------|------|--------------|
| 观看者/会员 | 查看真实余额、每笔变动和说明 | 不能充值、提现、转账或消费 |
| 客服人员 | 查询调币结果并处理用户申诉 | 不能直接改余额或发起高权限操作 |
| 财务运营 | 为明确业务原因发起加扣币、补偿或冲正 | 必须在授权额度和账号范围内 |
| 财务复核 | 独立批准高风险或批量调币 | 发起人与批准人必须不同 |
| 安全人员 | 处理异常频率、越权和负余额风险 | 可冻结请求，不能改写账本 |
| 审计人员 | 逐笔还原申请、审批、分录和余额 | 历史和审计均不可删除 |

## 5. User Stories

- 作为用户，我想看到当前金币余额和最后同步时间，以便知道页面是否是最新状态。
- 作为用户，我想查看每笔增加或扣减的数量、原因、时间和状态，以便理解余额变化。
- 作为用户，我想对不理解的调币记录发起申诉，并携带业务单号，以便客服定位。
- 作为财务运营，我想在提交前预览目标账号、变动方向、数量和变动后余额，以免误操作。
- 作为财务运营，我想用标准原因和用户可见说明记录业务依据，以便账本可解释。
- 作为复核人员，我想查看风险命中、发起人和变更前后余额，以便独立批准或拒绝。
- 作为运营负责人，我想批量处理活动补偿并查看逐项结果，以便失败项目可安全重试。
- 作为审计人员，我想通过原分录与冲正分录的关联还原纠错过程，以便证明历史未被篡改。
- 作为安全人员，我想在重复、高频、异常数量或负余额风险时阻止自动入账，以便降低滥用风险。

## 6. Requirements

### 6.1 Functional Requirements

#### 钱包与金币边界

- **WAL-FR-001**：每个账号最多拥有一个 App 金币钱包；金币是封闭式虚拟记账单位，不是法币、储值账户、加密资产或可提现收益。
- **WAL-FR-002**：App 1.0 只允许后台 `admin_credit`、`admin_debit`、`compensation`、`reversal` 和经审核的 `migration` 产生余额变化；用户侧不存在充值、赠礼、装扮购买、转账、提现或兑换入口。
- **WAL-FR-003**：钱包摘要至少返回权威余额、币种标识、账本版本和最后同步时间；客户端不得通过本地加减推导权威余额。
- **WAL-FR-004**：金币名称、图标和展示格式可配置，但权限、分录方向和数量使用稳定代码与整数最小单位；不得使用浮点数计算。
- **WAL-FR-005**：余额能否低于零及其阈值由 OQ-018 冻结；结论关闭前服务端 fail-closed，任何会导致负余额的扣币都不得自动生效。

#### 追加式账本

- **WAL-FR-006**：任何余额变化必须创建新 `wallet_entry`；禁止直接更新余额字段表达业务结果，禁止编辑或删除已生效分录。
- **WAL-FR-007**：分录至少包含稳定 entry ID、账号、方向、数量、原因代码、用户说明、内部业务引用、原分录引用、发起/批准主体、前余额、后余额、状态和服务端时间。
- **WAL-FR-008**：同一钱包的分录按服务端 sequence 串行写入；前余额必须等于上一生效分录的后余额，数量、方向和后余额满足确定性校验。
- **WAL-FR-009**：写入分录和更新余额快照必须在同一原子业务操作中完成；任一步失败均不得出现只有余额或只有分录的部分结果。
- **WAL-FR-010**：冲正通过新建与原分录方向相反且数量受约束的 `reversal` 分录完成；原分录保留并标记已冲正/部分冲正关系。
- **WAL-FR-011**：同一原分录的累计冲正数量不得超过原数量；重复冲正请求通过业务单号和幂等键返回原结果。
- **WAL-FR-012**：余额快照只作为查询优化，可随时由有效分录重建；对账发现差异时冻结相关调币并按 forward-fix 修复，不能重写历史。

#### 用户余额与明细

- **WAL-FR-013**：我的页面显示金币余额、规则说明和明细入口，不显示“充值”“去消费”“提现”“转账”或未来商品占位入口。
- **WAL-FR-014**：明细按服务端时间倒序、游标分页，支持全部、增加、扣减筛选；每项展示方向、数量、用户可见原因、时间和状态。
- **WAL-FR-015**：明细详情展示业务单号的用户安全版本、关联冲正、最终结果和申诉入口；不得暴露管理员身份、内部备注、风控规则或其他账号信息。
- **WAL-FR-016**：待复核申请不进入用户余额或明细；只有分录生效后才展示，失败/拒绝的后台申请不伪装成用户交易。
- **WAL-FR-017**：加币、扣币、补偿和冲正生效后生成必要站内通知，包含变动数量、用户说明和查看明细入口；页面打开时重新读取权威余额。
- **WAL-FR-018**：用户申诉必须关联具体分录或业务单号；申诉本身不冻结、删除或自动冲正分录，由授权流程给出结果。

#### 管理员单笔调币

- **WAL-FR-019**：财务运营通过稳定账号 ID、已验证登录标识或工单查找目标；结果显示脱敏账号、账号状态、当前余额和近期调币摘要，避免同名误调。
- **WAL-FR-020**：调币表单必须选择动作、输入正整数数量、标准原因、用户可见说明、内部备注和工单/活动引用；不能用负数同时表达方向。
- **WAL-FR-021**：提交前展示目标、方向、数量、前余额、预计后余额、重复/频率风险、是否需复核和用户最终可见文案。
- **WAL-FR-022**：每个调币申请拥有唯一业务单号、幂等键和请求哈希；同键同请求返回原状态，同键不同内容返回冲突。
- **WAL-FR-023**：申请状态至少包括 `draft`、`submitted`、`pending_approval`、`approved`、`executing`、`applied`、`rejected`、`cancelled`、`failed`、`reversed`。
- **WAL-FR-024**：金额、频率、批量、负余额风险、跨范围账号或异常模式任一超过配置阈值时进入双人复核；发起人不能批准自己的申请。
- **WAL-FR-025**：低风险操作是否允许授权内直接生效由 OQ-018 冻结；无明确生产配置时默认进入复核，不以客户端判断替代服务端规则。
- **WAL-FR-026**：复核页显示申请原文、目标摘要、前后余额、风险原因、同账号近期操作和发起人；批准/拒绝必须填写结论，批准时再次校验余额和账号状态。
- **WAL-FR-027**：批准不等于已入账；只有原子分录成功后状态变为 `applied`。执行失败保留失败原因和重试策略，不向用户发送成功通知。
- **WAL-FR-028**：财务运营、客服、复核、安全和审计角色职责分离；Owner 应急操作同样需要强认证、原因、告警和事后复核。

#### 批量调币与迁移

- **WAL-FR-029**：批量任务通过受控模板或 API 导入账号、方向、数量、原因和外部唯一引用；上传后先校验和预览，不立即入账。
- **WAL-FR-030**：批量任务必须进行账号存在性、重复引用、数量范围、预计总额、负余额、权限范围和异常集中度检查，并强制独立复核。
- **WAL-FR-031**：批量执行逐项幂等，单项结果包括 applied、rejected、failed、duplicate 和 skipped；一个失败不得回滚或重做已成功项目。
- **WAL-FR-032**：任务支持暂停尚未执行项目、导出逐项结果和仅重试可重试失败；不得重新执行已 applied 项。
- **WAL-FR-033**：旧余额迁移必须有源快照、提取时间、映射规则、目标账号、校验哈希和逐项结果；迁移分录与日常调币原因区分。

#### 审计、对账与分析

- **WAL-FR-034**：申请、编辑草稿、提交、复核、执行、失败、取消、冲正、批量暂停和敏感查询均写审计事件；审计只引用账务对象，不复制内部备注到分析。
- **WAL-FR-035**：系统至少执行钱包余额快照与分录汇总、调币申请与分录、原分录与冲正、通知与生效结果的定期对账。
- **WAL-FR-036**：未解释差异、重复业务单、sequence 断裂、超额冲正、异常负余额和审计缺失触发高优先级告警，并冻结受影响范围的新调币。
- **WAL-FR-037**：至少记录钱包页面曝光、明细筛选、分录详情、申诉入口、调币创建/复核/生效/失败、批量结果和冲正事件。
- **WAL-FR-038**：运营看板按原因、方向、状态、操作范围和时间统计数量、总额、失败率、复核率和差异；不得公开用户余额榜或操作员调币榜。

### 6.2 主流程

#### 单笔管理员调币

```text
查找并确认目标账号
→ 选择加币/扣币/补偿/冲正并填写依据
→ 服务端预览前后余额与风险
→ 提交幂等申请
→ 低风险授权内执行 / 高风险等待独立复核
→ 再次校验账号和余额
→ 原子追加分录并更新余额快照
→ 生成站内通知和审计事件
→ 对账任务验证申请、分录和余额
```

#### 用户查看争议分录

```text
进入金币页
→ 拉取权威余额与账本版本
→ 游标加载明细
→ 打开分录详情查看原因和关联冲正
→ 如有疑问，携带安全业务单号创建申诉
→ 客服按授权查询，不直接修改余额
```

### 6.3 权限矩阵

| 动作 | 用户 | 客服 | 财务运营 | 财务复核 | 安全 | 审计 |
|------|------|------|----------|----------|------|------|
| 查看本人余额/明细 | 是 | 工单最小摘要 | 授权范围 | 复核范围 | 风险案件 | 受控只读 |
| 发起单笔调币 | 否 | 否 | 是 | 否 | 否 | 否 |
| 批准高风险/批量 | 否 | 否 | 否 | 是，非发起人 | 可冻结 | 否 |
| 执行冲正 | 否 | 只能申请支持 | 按权限发起 | 高风险批准 | 可冻结 | 否 |
| 修改/删除分录 | 否 | 否 | 否 | 否 | 否 | 否 |
| 导出批量结果 | 否 | 否 | 自己/授权任务 | 复核任务 | 案件范围 | 受控 |
| 查看内部备注 | 否 | 工单必要部分 | 自己/授权范围 | 复核范围 | 案件范围 | 审计范围 |

### 6.4 异常与恢复矩阵

| 场景 | 用户/后台表现 | 服务端规则 | 恢复方式 |
|------|---------------|------------|----------|
| 重复提交 | 返回原业务单状态 | 不重复入账 | 使用原单继续查询 |
| 扣币将导致负余额 | 预览/执行被阻止 | fail-closed，除非已冻结政策允许 | 调整数量或获得合规结论 |
| 批准后余额已变化 | 执行显示并发冲突 | 重新校验，不沿用旧预览 | 返回复核/重新提交 |
| 分录成功、通知失败 | 余额和明细正确 | 不回滚账本 | 按原事件防重补发通知 |
| 批量部分失败 | 展示逐项结果 | 成功项不回滚、不重做 | 仅重试可重试失败 |
| 误调币 | 原分录保留 | 创建受控冲正 | 走复核并通知用户 |
| 余额对账差异 | 页面可显示维护提示 | 冻结受影响调币 | 重建快照并 forward-fix |
| 客户端离线 | 显示缓存与最后同步时间 | 不允许本地改余额 | 联网后拉取权威版本 |

### 6.5 Non-Functional Requirements

- **WAL-NFR-001**：钱包写入使用 D1 事务/等价原子边界和账号级并发控制；不得产生部分分录或余额覆盖。
- **WAL-NFR-002**：数量使用整数并验证溢出、方向、上限和 sequence；所有关键写接口强制幂等。
- **WAL-NFR-003**：钱包、分录、申请和批量文件是敏感数据，按对象级权限访问，禁止共享缓存和公共 URL。
- **WAL-NFR-004**：日志和分析不得记录完整内部备注、上传原文件、账号登录标识或敏感风控阈值。
- **WAL-NFR-005**：余额读取、分录分页、申请执行和批量任务具备性能指标、容量预算、积压告警和恢复 Runbook。
- **WAL-NFR-006**：用户明细和后台财务流程支持动态字体、屏幕阅读器、键盘、缩放及正负方向的非颜色表达。
- **WAL-NFR-007**：账本与审计备份、恢复和重建必须经过演练；灾难恢复后余额与分录汇总完全一致。

### 6.6 实施前门禁

| 门禁 | 对应决策 | 未关闭时允许继续 | 未关闭时禁止 |
|------|----------|------------------|------------|
| 调币阈值、负余额、批量复核 | OQ-018 | 状态机、预览、账本和配置结构 | 财务后台生产启用 |
| 账务与审计保留 | OQ-020 | 追加模型与隔离设计 | 冻结清理/归档 migration |
| 数据位置与生产适用性 | OQ-024 | 本地/测试数据验证 | 接入生产钱包数据 |
| Cloudflare 容量预算 | OQ-031 | 小规模事务和对账验证 | 批量扩量 |

## 7. Acceptance Criteria

- **WAL-AC-001**：Given App 1.0 用户进入金币页，When 数据加载完成，Then 只看到余额、明细、规则和申诉入口，不存在充值、消费、转账或提现入口。
- **WAL-AC-002**：Given 财务运营发起一次加币，When 分录生效，Then 余额增加正确数量、产生唯一追加分录、站内通知和审计事件。
- **WAL-AC-003**：Given 相同幂等键的调币请求重复到达，When 请求内容一致，Then 返回同一申请/分录，余额只变化一次。
- **WAL-AC-004**：Given 高风险调币待复核，When 发起人尝试批准，Then 服务端拒绝，用户余额和明细均不变化。
- **WAL-AC-005**：Given 扣币会导致未获允许的负余额，When 提交或执行，Then 服务端 fail-closed，不产生分录或成功通知。
- **WAL-AC-006**：Given 已生效分录需要纠错，When 通过冲正流程完成，Then 原分录不可修改，新分录与原分录关联且最终余额可重建。
- **WAL-AC-007**：Given 批量任务中部分账号无效，When 执行完成，Then 有效项只入账一次，无效项逐项失败，重试不会重复成功项。
- **WAL-AC-008**：Given 分录已成功但通知暂时失败，When 通知恢复，Then 账本不回滚，补发只生成一条通知。
- **WAL-AC-009**：Given 余额快照被测试性破坏，When 运行重建与对账，Then 可由有效分录恢复一致余额并产生差异审计。
- **WAL-AC-010**：Given 用户打开某条调币明细，When 查看详情，Then 能理解数量、方向、原因、时间和冲正关系，但看不到内部备注或管理员隐私。
- **WAL-AC-011**：Given 待复核、被拒绝或失败的调币申请，When 用户查看钱包，Then 不出现在余额和账本明细中。
- **WAL-AC-012**：Given 任一管理员试图直接修改余额或删除分录，When 请求到达服务端，Then 被拒绝并记录高优先级审计事件。

## 8. Out of Scope

- App 1.0 用户金币充值、消费、礼物、装扮、转账、提现、法币兑换和概率商品。
- 向真人或其他用户分成、结算或形成可提现收益。
- 管理员直接改余额、编辑/删除历史分录或覆盖原调币原因。
- 用负数同时表示加币和扣币，或使用浮点数保存数量。
- 未经独立复核的高风险、批量或异常调币。
- 将待复核申请显示为用户已到账/已扣除结果。
- 用通知中的历史余额替代钱包权威查询。
- 后续商店订单、退款、礼物消费和装扮库存对账；这些能力需独立 Feature 立项。
